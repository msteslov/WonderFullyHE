# Дорожная карта bootstrap-конвейера

## Цель

Bootstrap в проекте должен быть не монолитной процедурой, а конфигурируемым конвейером. Каждая стадия имеет явный контракт, несколько реализаций и единый формат отчёта. Сейчас каркас фиксирует уровень, scale и время; точность, память, число rotations и key switching добавляются вместе с reference oracle и experiment runner.

Алгоритм включается в pipeline только после сравнения с альтернативами на одном профиле, наборе входных данных и критериях точности. Непроверенная или просто первая реализованная версия остаётся reference/experimental-вариантом и не становится вариантом по умолчанию.

```text
входной ciphertext
  -> ModUp strategy
  -> CoeffToSlot strategy
  -> EvalMod strategy
  -> SlotToCoeff strategy
  -> выходной ciphertext
```

## Базовый слой

`SealAdapter` готов как слой независимых примитивов: кодирование, шифрование, арифметика, `relinearize`, `rescaleToNext`, `modSwitchTo`, ротации, ключи и сериализация. Он не должен содержать реализацию bootstrap-стадий или скрывать порядок операций.

`alignForAddition` остаётся узкой операцией согласования близких scale для сложения; policy выбора scale должна находиться в стратегии, которая её вызывает.

## Компоненты, которые требуется реализовать

1. **Контракты pipeline.** Реализованы `BootstrapStage`, `BootstrapPipeline`, требования к ключам и отчёт по стадиям. Каркас не содержит алгоритмов и не выбирает стратегию по умолчанию.
2. **Планировщик ключей.** По конфигурации должен заранее вычислять необходимые Galois/relinearization keys, их размер и допустимые rotation steps.
3. **ModUp стратегии.** Нужны отдельные проверяемые реализации basis extension. Ручной ModUp не должен возвращаться в `SealAdapter`.
4. **CoeffToSlot и SlotToCoeff стратегии.** Базовый DFT-путь уже есть как исследовательская модель; далее нужны сравнимые реализации dense diagonal, BSGS и FFT-like с единым интерфейсом.
5. **EvalMod стратегии.** Нужны разделённые сущности: модель аппроксимации, способ вычисления полинома и политика scale/levels. Chebyshev и Paterson–Stockmeyer должны быть независимыми переключателями.
6. **Планировщик scale и уровней.** До запуска pipeline он обязан проверять, что каждая стадия имеет достаточный modulus chain и что сложения совместимы по уровню/scale.
7. **Reference oracle и тесты.** Для каждой стадии нужны plaintext/reference проверки, для каждой связки — расшифрованная точность и инварианты уровня/scale.
8. **Experiment runner.** Единый запуск комбинации стратегий с JSON/CSV-отчётом: параметры, расход ключей, время, peak memory, уровни и ошибка.

## Порядок работы

К полноценному encrypted bootstrap переходить ещё рано. Следующий шаг — реализовать и проверить первую ModUp-стратегию на реальных ciphertext, затем добавить planner ключей и уровней. После этого DFT и EvalMod подключаются через общие контракты. End-to-end bootstrap допустимо запускать только после появления reference oracle, планировщика уровней и отчёта по каждой стадии.
