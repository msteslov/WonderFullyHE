# План честного сравнения CoeffToSlot

Этот документ задаёт обязательные условия до сравнения `CoeffToSlotFftPlan` и
`CoeffToSlotBsgsPlan`. Его цель — исключить ситуацию, когда измеряется разница
между случайно разным качеством реализаций, а не между стратегиями.

## Граница текущего эксперимента

Пока `ModUp` не реализован и не проверен, сравнивается только исполнение одной
и той же forward DFT-матрицы над synthetic slot fixture. Результат не является
оценкой полного CKKS bootstrapping и не разрешает включать ни один план в
runtime bootstrap.

## Общая постановка

Перед запуском benchmark фиксируются и записываются в отчёт:

- идентификатор `BootstrapCandidate` и его CKKS-параметры;
- число активных слотов и размер DFT;
- входной диапазон комплексных значений, входной scale и допустимое отклонение
  scale после операции;
- эталонный plaintext-результат через `CanonicalEmbeddingReference` или
  прямую DFT с тем же порядком слотов;
- частный лимит ошибки кандидата `errorBudget.coeffToSlot` (сейчас `2e-10`);
- число повторов, прогрев и способ агрегации времени (медиана и минимум);
- версию компилятора, тип сборки и параметры машины.

Ни один план не участвует в сравнении, если `preflightCoeffToSlot` не готов,
точность выше бюджета, расход уровней не соответствует заявленному или набор
rotation keys неполный.

## Что требуется довести до измерения

### Общее для обоих вариантов

1. Добавить единый benchmark, который измеряет только `apply`: шифрование,
   plaintext reference, генерация ключей и расшифрование не входят во время
   исполнения плана.
2. Отдельно измерять подготовку: построение плана, генерацию rotation keys и
   сериализованный размер evaluation keys.
3. Использовать один входной ciphertext, один профиль и один набор активных
   слотов для сравниваемой пары.
4. Перед каждым замером проверять результат относительно plaintext-эталона и
   фиксировать максимальную абсолютную ошибку.
5. Исключить из горячего участка повторное выделение памяти и кодирование
   неизменяемых plaintext-диагоналей: план должен подготовить их один раз на
   требуемом уровне и scale.

### FFT

1. Зафиксировать допустимые размеры radix-2 и порядок слотов.
2. Подтвердить полный набор rotations, включая bit-reversal, без неучтённых
   бесплатных перестановок.
3. Проверить, какие слои можно слить без изменения математики, scale и
   подтверждённой границы ошибки.
4. Подготовить диагонали/константы слоёв вне измеряемого `apply`.

### BSGS

1. Для каждого размера DFT перебрать допустимые `babyStep`: делители и
   ближайшие к квадратному корню размера значения.
2. Для каждого `babyStep` измерить runtime, число уникальных rotations,
   размер ключей, расход уровней и ошибку.
3. Выбрать BSGS-конфигурацию только из вариантов, прошедших одинаковые
   точностные и ресурсные ограничения.
4. Подготовить baby ciphertext и plaintext-диагонали так, чтобы в измеряемом
   участке оставались только необходимые homomorphic операции.

## Метрики отчёта

Для каждой строки «профиль × размер DFT × стратегия × параметры стратегии»
отчёт обязан содержать:

| Метрика | Значение |
| --- | --- |
| Максимальная абсолютная ошибка | относительно эталона |
| Время `apply` | минимум, медиана, число повторов |
| Расход уровней | фактический `chainIndex` до/после |
| Scale | log2 до/после |
| Rotation steps | полный уникальный список и количество |
| Размер evaluation keys | байты сериализованного набора |
| Память плана | байты подготовленных plaintext-диагоналей |

## Правило выбора

Сначала отбрасываются конфигурации, не прошедшие preflight, лимит ошибки,
доступную память или заданный лимит ключей. Из оставшихся вариантов победитель
выбирается отдельно для каждого профиля:

1. при цели минимальной задержки — минимальная медиана времени `apply`;
2. при равном времени в пределах заранее заданного шума — меньший размер keys;
3. при равенстве и здесь — меньший расход уровней;
4. если компромисс существенный, в библиотеке остаются несколько профилей с
   явно названной целью, а не один ложный универсальный победитель.

До появления такого отчёта FFT и BSGS остаются исследовательскими кандидатами:
оба могут использоваться в тестах и benchmark, но ни один не считается
оптимальным или основным алгоритмом библиотеки.
