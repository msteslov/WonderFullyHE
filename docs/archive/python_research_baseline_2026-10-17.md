# Python baseline: CKKS, bootstrap и CoeffToSlot

Дата запуска: 17 октября 2026 года. Базовая ревизия: `314cec9e1a02`.
Рабочее дерево содержало незакоммиченные изменения; это состояние сохранено в
метаданных запуска.

## Воспроизведение

```bash
python3 -m venv python/.venv
python/.venv/bin/pip install -e 'python[dev]'
python/.venv/bin/wfhe-experiments run python/configs/research.json
```

Прогон создал 884 нормализованные записи. Конфигурация включает пять CKKS-профилей,
93 результата исследования цепочки модулей, 35 результатов parallel throughput,
36 результатов bootstrap-кандидатов, по три запуска пяти факторизаций CoeffToSlot
и пять запусков полного bootstrap fixture.
Для каждой группы рассчитываются среднее, медиана, минимум, максимум, стандартное
отклонение и нормальное приближение 95%-го доверительного интервала.

## Основные наблюдения

### Профили CKKS

Для операции multiply-relinearize-rescale профиль `high_precision_ckks` показал
среднюю максимальную ошибку примерно в 15 100 раз меньше, чем `basic_ckks`, при
3.02-кратной задержке. Это наблюдаемый компромисс, а не универсальная оценка:
профили имеют разные параметры, а запуск выполнен на одной машине.

### Глубина и цепочка модулей

`depth2` не выполняется при одном рабочем уровне. `depth3` не выполняется при одном
и двух рабочих уровнях. После достижения необходимой длины дополнительный уровень
не дал монотонного уменьшения ошибки: наблюдаемая worst-case ошибка оставалась
порядка `1e-8`. Это согласуется с гипотезой, что неиспользуемые уровни сами по себе
не улучшают точность фиксированного вычисления.

### Parallel throughput

Все 20 строк `basic_ckks` получили `FAIL` по встроенному критерию `1e-9` и исключены
из допустимого сравнения. `high_precision_ckks` прошёл тот же критерий во всех 15
строках. Его средняя пропускная способность выросла с 281 задач/с на одном потоке
до 787 задач/с на четырёх потоках, то есть в 2.80 раза.

### CoeffToSlot

| Факторизация | Warm apply, мс | Prepared bytes | Mean second error |
|---|---:|---:|---:|
| `candidate_0` | 322.85 | 277 112 784 | `9.33e-11` |
| `candidate_1` | 314.77 | 280 783 152 | `8.98e-11` |
| `candidate_2` | 381.96 | 251 420 208 | `8.76e-11` |
| `candidate_3` | 559.18 | 308 310 912 | `8.71e-11` |
| `candidate_4` | 555.22 | 367 036 800 | `8.99e-11` |

`candidate_1` дал минимальную среднюю warm-задержку, а `candidate_2` — минимальный
объём подготовленных plaintext. Усреднение по всем факторизациям показало warm
применение на 5.4% медленнее первого; `candidate_0` и `candidate_1` ускорились, но
остальные регрессировали. Гипотеза об универсальном warm-ускорении не подтверждена.
Все наблюдаемые ошибки оставались порядка `1e-10`.

### Bootstrap candidates

Минимальное среднее время генерации ключей в этом запуске получено для
`validation_16_s55`: 11.55 мс. Размер Galois keys составил 3 212 224 байта.
`validation_4_s55` был близок — 12.11 мс и 1 638 908 байт. Увеличение числа
активных слотов и degree сопровождалось ростом набора ключей; причинный вывод
требует отдельного контролируемого эксперимента.

### End-to-end fixture

Полный маршрут ModRaise → CoeffToSlot → EvalRound → SlotToCoeff выполнен пять раз.
Все пять запусков прошли: среднее время `apply` составило 1.00 мс, среднее полное
время — 28.07 мс, средняя наблюдаемая ошибка — `5.485e-11`. Трасса содержит 125
узлов и использует 11 уровней.

Этот запуск использует профиль `N=16` и явное `TestOnlyAssumption(K=1)`, записанное
в результатах для отделения fixture от конфигураций с внешним lift-контрактом.

## Ограничения

- запуск сделан из dirty worktree и должен быть повторён после фиксации ревизии;
- использована одна аппаратная и программная конфигурация;
- число внешних повторов равно трём или пяти;
- normal-approximation CI при малом числе повторов служит ориентиром;
- CoeffToSlot характеризует реализованную стадию, а не полностью сертифицированный
  production bootstrap;
- failed throughput-строки не являются допустимым performance baseline.
